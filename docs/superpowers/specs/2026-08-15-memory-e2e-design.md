# Memory E2E Evaluation Design

- Date: 2026-08-15
- Status: approved for implementation
- Target: OmniRoute v4.0 four-layer memory (L0–L3)

## Goal

Automate the complete memory evaluation flow against a real isolated OmniRoute server using CLI/HTTP APIs rather than browser UI. The suite must verify that the gateway captures raw conversation into L0, distills L1/L2/L3, and produces reproducible semantic-quality evidence.

## Profiles

One harness, two execution profiles:

| Profile | Upstream models | Cost | Purpose |
| --- | --- | --- | --- |
| `smoke` | Built-in mock provider | Free | Verify server startup, seeding, API key creation, L0 import, gateway capture, explicit distillation, worker lifecycle, L1–L3 persistence, and report generation. |
| `live` | Configurable real provider/model, initially DeepSeek for generation, distillation, and judging | Real token cost | After the system path passes, evaluate semantic memory quality using an LLM judge. |

Both profiles are end-to-end. Live retains the smoke gate so infrastructure failures are not misreported as memory-quality failures.

Commands:

```bash
npm run test:memory-e2e:smoke
npm run test:memory-e2e:live
```

Both are explicit to prevent accidental live-token spend.

## Isolation and seeding

Every run creates:

- An isolated temporary `DATA_DIR`.
- A dedicated test server process and port.
- A subject OmniRoute API key with memory capture and injection enabled.
- A separate judge API key with capture and injection disabled.
- Distinct run and session IDs for every fixture.
- A separate report directory.

Provider configuration is automated through product APIs (or a dedicated seeding path where an API is unsuitable). No browser interaction is required. Credentials come from environment variables or a local uncommitted config file and are never written to reports.

For the first implementation, generation, distillation, and judge models use DeepSeek. These are runtime configuration values, not hardcoded model identities:

```json
{
  "subject": { "provider": "deepseek", "model": "deepseek-chat" },
  "distillation": { "provider": "deepseek", "model": "deepseek-chat" },
  "judge": { "provider": "deepseek", "model": "deepseek-chat" }
}
```

A future version can switch the judge to MiniMax without changing harness architecture.

## Conversation fixture model

The harness uses multi-turn templates. Fixture history ends with an assistant message. The final user message is not imported; it is sent through the real OmniRoute gateway. DeepSeek generates the final assistant response, and the gateway captures both messages.

The final L0 sequence is:

```text
user_1, assistant_1, ..., user_n-1, assistant_n-1,
final_user (real gateway request), final_assistant (real model response)
```

History import happens through a formal authenticated L0 import API and CLI:

```bash
omniroute memory l0 import ./case-01.json \
  --api-key-id <id> \
  --session <session-id>
```

Import input allows only `role` and `content`. Timestamps are generated by the importer in array order, ensuring monotonic ordering without depending on historical runtime timestamps. Imported records use `source="imported"`.

## Test suites

There are twelve equally weighted suites: ten foundational suites and two composite stress suites.

| ID | Domain | Focus |
| --- | --- | --- |
| 01 | Engineering collaboration preferences | Long-term tools, code style, communication preferences |
| 02 | Project facts and decisions | Technical choices, rationale, owners, timeline evolution |
| 03 | Multi-scene task execution | Task state, visible tool outcomes, L2 scene grouping |
| 04 | User identity and behavioral profile | Persona, naming, habits, stability under noise |
| 05 | Complex constraints and safety rules | Must-retain constraints, prohibitions, exceptions |
| 06 | Preference changes and overrides | Correct handling of superseded preferences and conflicts |
| 07 | Cross-session entity relationships | Team/project/account/resource mappings |
| 08 | Failure and recovery experience | Root causes, remediation, prevention |
| 09 | Mixed-language naming conventions | Chinese/English mixing, casing, proper nouns |
| 10 | Long-context compression | High-value fact selection without losing constraints or hallucinating |
| 11 | Composite: combines themes 01–05 | Cross-topic distinction, scene splitting, persona stability |
| 12 | Composite: combines themes 06–10 | Override resolution, entity evolution, recovery, naming, compression under density |

Language policy: suites are primarily Chinese. Suite 09 and both composite suites deliberately exercise Chinese/English mixing and identifier fidelity.

Each fixture defines:

- Multi-turn `history`.
- `finalUser`.
- Mandatory semantic points.
- Negative points (temporary or irrelevant information that should not be promoted).
- Layer-specific rubrics for L1/L2/L3.

## L0 gate

L0 is raw visible memory, not an audit log. It records user and assistant visible text and does not store system prompts, reasoning, tool calls, tool results, raw request bodies, token usage, or headers.

Before semantic scoring, the harness strictly verifies:

1. Owner and session isolation.
2. Correct chronological role order.
3. Imported history fidelity.
4. Final user fidelity against the actual gateway request.
5. Final assistant fidelity against the actual gateway response.
6. No duplicate history from context replay.
7. `truncated=false` and `is_internal=false`.
8. Subject provider/model match.
9. Correlation traceability.
10. L1 references real L0 message IDs.

Only protocol-necessary whitespace/JSON normalization is allowed. L0 failure stops semantic evaluation for that fixture.

## Distillation orchestration

The main evaluation path explicitly triggers distillation through a formal authenticated API and CLI:

```http
POST /api/memory/distillation/run
```

```bash
omniroute memory distillation run \
  --api-key-id <id> \
  --session <session-id> \
  --layers l1,l2,l3 \
  --wait \
  --timeout 180000
```

Distillation runs sequentially:

```text
L0 -> L1 -> L2 -> L3
```

Each layer must complete before the next starts. If L1 fails, L2 and L3 stop for that fixture. If L2 fails, L3 stops. The remaining fixtures still execute.

Default polling interval is two seconds, with a 180-second per-layer timeout. Failures include task/DLQ evidence. Automatic retries are not performed; a rerun requires a new run ID.

The automatic background worker is tested separately for start/stop, interval, concurrency, and lifecycle behavior; it does not carry the main twelve-fixture evaluation.

## LLM judging

Judge calls go through the OmniRoute gateway using a separate judge API key and owner. Capture and injection are disabled for the judge key. Judge temperature is zero and retries default to zero.

The judge receives:

- Real L0 transcript.
- Distilled L1/L2/L3 output.
- Mandatory points.
- Negative points.
- Layer responsibility definitions.
- Scoring rubric.

It returns strict JSON. JSON parse or schema validation failure is recorded as an evaluation failure rather than silently retried.

Judge output includes per-layer scores, mandatory point scores, rationale, evidence, and hallucination flags.

## Passing thresholds

The strict thresholds are:

- 12/12 suites pass.
- Overall mean score at least 4.5.
- Every layer mean score at least 4.5.
- Every mandatory semantic point scores at least 4.
- Any hallucination vetoes the suite.
- Any L0 gate failure fails the suite.
- Any distillation failure fails the suite.

Judge models sharing a provider/model with distillation are flagged in the report because self-preference bias is possible. First-version scores are best used for relative regression comparison rather than absolute quality claims.

## Reports

Each run creates:

```text
test-results/memory-e2e/<run-id>/
  report.md
  report.json
  summary.csv
  fixtures/
  server.log
  seed.json
  metadata.json
```

The report includes:

- Overall PASS/FAIL and profile.
- Foundational and composite group statistics.
- L0 gate result for each suite.
- L1/L2/L3 generation status.
- Judge scores and mandatory point coverage.
- Failure stage attribution.
- Token/cost data.
- Model configuration.
- Evidence file references.

API keys are masked. Authorization headers and credentials are scrubbed from server logs. Fixture artifacts retain actual transcripts and distilled memory content for manual review.

## Implementation layout

```text
scripts/memory-e2e/
  run.ts
  config.ts
  server.ts
  seed.ts
  gateway.ts
  l0Import.ts
  distillation.ts
  gate.ts
  judge.ts
  report.ts
  types.ts

tests/fixtures/memory-e2e/
  case-01-engineering-preferences.json
  ...
  case-12-composite-advanced.json
```

The main runner is a Node CLI/HTTP harness, not a browser test. It owns the isolated server lifecycle. A thin Playwright UI smoke may be added separately, but browser multimodal evaluation is intentionally avoided.
